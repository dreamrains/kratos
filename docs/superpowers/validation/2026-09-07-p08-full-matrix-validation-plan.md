# P08：真实浏览器与真实 Provider 全矩阵验证方案

日期：2026-09-07
状态：`executed_incomplete / not_accepted`（最新 R19 因产品侧上传/运行链路未完成 M01—M06 全矩阵；不得归为外部未决，结果见[阶段记录 P08-R19](2026-09-06-value-preservation-stage-records.md)）

## 1. 背景与调整

P7 已建立离线回归和本地真实浏览器证据，用于验证工具、会话、SSE、持久化、导出和已知失败边界。P08 的目的不是重复制造单点探针或为旧验证工具链背书，而是在真实浏览器和真实 Provider 共同参与时，系统性收集真实语义、分析质量和端到端流程问题。

本方案替代此前按单场景冻结、单场景恢复和历史批次容量继承的真实调用执行思路。历史真实 Provider 批次、摘要、调用额度、执行器和收据只作历史资料，不能成为本次 P08 的输入、授权或结论。

## 2. 目标、范围和非目标

### 目标

1. 在同一轮有效验证中完成整个 P08 矩阵，收集跨场景的真实问题，而不是在第一个普通失败后中断。
2. 区分系统性全局异常、核心流程问题和交互呈现问题，使修复优先级服从分析可信度与任务完成能力。
3. 让每个问题都关联到浏览器现象、Provider 调用记录、会话与数据归属、导出或持久化证据，避免凭主观印象修复。
4. 验证同一套受限事实在不同表达、跨轮追问、刷新和导出后仍保持可信边界。

### 范围

- 当前受控提交、隔离测试数据、真实浏览器、真实 Provider 和现有产品 Web/SSE/AgentLoop 路径。
- 真实模型的意图理解、工具选择、回答质量、确认交互、发布边界、竞争假设与身份适配。
- 每个场景完成后的本地只读证据核查，以及所有场景结束后的统一问题归纳。

### 非目标

- 不把本次验证视为 staging、生产或部署验收。
- 不在矩阵执行中临时加题、换模型、换端点、改阈值或补做“验证性探针”。
- 不在任一普通场景失败后即时修复、重跑该场景或把其结果改写为通过。

## 3. 核心原则

| 原则 | 执行规则 |
|---|---|
| 全矩阵优先 | 只要没有系统性全局异常，完整执行 M01—M06；单个场景的功能、语义、交互或导出失败仅记录为该场景失败。 |
| 先收集后修复 | 执行期间只记录事实与证据，不改代码、不改场景、不重跑；全部场景结束后统一聚类、判因和排优先级。 |
| 核心流程优先 | 数据归属、工具执行、可信发布、确认、会话恢复、Provider 调用核算和假设状态流转优先于样式、文案和非阻断交互。 |
| 证据分级 | 单元/离线、本地浏览器、真实浏览器+真实 Provider、部署/生产分别记录，互不替代。 |
| 当前批次独立 | 每次真实调用前重新确认当前提交、输入、模型、端点、预算、矩阵版本和报告位置；不复用历史摘要、额度或授权。 |

## 4. P08 矩阵

| ID | 业务目标与操作 | 核心断言 | 主要证据 |
|---|---|---|---|
| M01 | 中文分析请求：加载销售数据并要求给出行动建议 | 真实模型完成分析；数值、范围和限制基于工具结果；建议有触发条件与停止条件 | 浏览器回答、工具收据、已验证结论、刷新后的会话 |
| M02 | D7 留存分析并要求判断 D30 | 发布 D1—D7 实测结果；D30 可以保持未知，也可以作为明确标注的拟合外推情景发布，但必须命名模型族、披露拟合度、声明未留出/回测/验证、展示模型敏感性，并由宿主按回执参数逐值重算；不得写成已经验证的预测 | 浏览器流式内容、curve-fitting 回执、宿主重算结果、修订/发布状态、导出 |
| M03 | 六来源金额变化并明确要求保留全部来源 | 六个来源均进入发布包与导出；金额、记录数和来源不被静默裁剪 | 发布包、Markdown、压缩后的收据与导出 |
| M04 | 创建竞争假设，追加支持与反证，再更新数据版本 | 关系由真实工具证据驱动；状态按未决/支持/冲突/失效流转；历史证据可审计 | 假设集、证据绑定、Workbench、刷新后状态 |
| M05 | 对同一可信结论连续以业务、分析师、管理者、大白话、技术身份追问 | 事实、范围、限制和证据等级不变；表达按身份变化且可恢复技术表达 | 连续浏览器对话、会话持久化、导出 |
| M06 | 复合请求：分析、确认、失败提示、刷新与导出 | 确认只在业务语义缺口处出现；错误不伪装完成；会话/SSE/导出状态一致 | 确认事件、运行状态、浏览器页面、会话文件 |

M01—M06 与 B01—B06 一一对应，但使用真实 Provider 的自然响应；不要求模型复述脚本化答案，也不因措辞不同判定失败。

## 5. 一次验证批次的执行步骤

### 5.1 执行前：零调用准备

1. 记录当前提交、工作区状态、矩阵版本、隔离目录、测试数据摘要、模型、端点、最大调用数、报告路径和执行时间。
2. 运行当前提交的离线回归与本地浏览器健康检查；失败时只记录是否构成系统性全局异常，不用历史结果替代。
3. 在真实浏览器确认 Provider 配置可见、测试目录为空且与用户会话隔离；此步骤不发送分析请求。
4. 将 M01—M06 的输入、预期断言和最大调用数一次性冻结。调用预算按六个场景的正常回合总和加明确余量制定，禁止执行后按失败结果加码。
5. 取得用户对本次冻结批次的明确 Provider 授权后，才允许发送 M01 的第一条请求。

### 5.2 执行中：完整收集

1. 按 M01 至 M06 顺序在真实浏览器执行，每个场景使用独立会话和隔离数据。
2. 每场景完成正常所需的上传、发送、真实确认、刷新和导出；不使用直接 API chat、脚本化模型或手工改写会话状态。
3. 对每个场景记录：请求和响应时间、实际 Provider 调用数、工具与收据、确认事件、页面结果、刷新结果、导出文件、控制台异常和失败原因。
4. 普通失败仍继续下一场景。禁止在执行中修代码、改 fixture、调整 oracle、重跑失败场景或补发新问题。
5. 批次结束后关闭本地服务，只保留隔离目录与只读证据。

### 5.3 执行后：统一分析与修复

1. 每个场景必须分别记录四个维度，不能用单一“看起来完成”覆盖其中任一失败：
   - **执行与生命周期**：上传、工具、确认、终态、deadline 和任务状态是否闭合；
   - **证据与主张有效性**：数值、来源、范围、拟合参数、限制和结论是否绑定并可复算；
   - **分析价值与需求覆盖**：是否回答用户问题、区分已计算/未计算/证据不足，并给出可执行但不过度的下一步；
   - **传输、持久化与呈现一致性**：SSE、刷新、Workbench、压缩和导出是否投影同一结果。
2. 每个维度使用 `passed`、`product_failed`、`external_inconclusive` 或 `not_run`。场景只有四维均为 `passed` 才是 `passed`；任一维为 `product_failed`，场景即失败。
3. `external_inconclusive` 只适用于外部 Provider/网络结果不可判定，且产品自己的调用账本、120 秒 deadline、SSE 恢复、持久化和唯一终态均正常工作的情形。产品卡死、上传失败未恢复、deadline 未生效、事件不闭合或状态不一致必须记为 `product_failed`，不得用外部未决降级隐藏。
4. 以共同根因聚类，不按页面数量重复计数。例如同一 SSE 会话绑定错误可同时解释刷新、Workbench 和导出异常。
5. 先处理 P0/P1 核心流程问题；完成修复和离线回归后，开启新的完整 M01—M06 批次验证，不能只重跑先前失败项。
6. 交互、文案、布局和非阻断可读性问题在不影响核心流程时列为 P2，和核心修复分开排期。

## 6. 系统性全局异常与停止规则

只有以下情形可以停止整个矩阵；停止时保留已完成场景，明确剩余场景为 `blocked` 或 `not_run`：

| 全局异常 | 判定方式 | 处置 |
|---|---|---|
| 批次身份不一致 | 当前提交、测试数据、模型、端点、矩阵或预算与执行前记录不一致 | 零调用停止，重新准备新批次 |
| 无法建立可信调用账本 | 无法将请求、Provider 消耗、会话和数据归属一一对应，或账本缺失/损坏/超额 | 立即停止，保留现有证据，不推断消耗 |
| 账户或基础服务全局不可用 | 凭据无效、配额耗尽、Provider 整体不可达，导致无法开始或持续执行多个场景 | 停止，记录已知消耗与错误，不切换模型或端点 |
| 数据或会话隔离失效 | 跨会话、跨数据集或用户数据暴露；测试数据归属无法建立 | 立即停止并提升为 P0 |
| 浏览器/服务基础链路整体不可用 | 无法加载页面、无法发送任何请求或所有场景共享同一启动失败 | 停止并先修复基础链路 |

下列问题**不是**全局停止理由：单个工具失败、单个模型回答差、某场景确认不合理、某次导出缺失、页面样式/文案问题、某个假设状态错误、单个场景的 Provider 响应失败。它们必须记录，并继续执行其余可达场景。

## 7. 问题分级与修复顺序

| 优先级 | 定义 | 例子 | 修复后验证 |
|---|---|---|---|
| P0 | 可信度、隔离或调用核算全局失效 | 错会话/错数据、伪造 verified、调用数未知、超预算 | 修复后新建完整矩阵批次 |
| P1 | 核心分析流程不可完成或结论不可信 | 工具结果未发布、越界预测、来源丢失、确认阻塞、刷新丢失、假设错误升级 | 修复后新建完整矩阵批次 |
| P2 | 流程可完成但表达或交互不合格 | 身份措辞不自然、布局溢出、非阻断导出样式、提示文案 | 与 P0/P1 分开排期；修复后按影响范围安排下一完整矩阵 |

问题记录至少包含：场景、步骤、预期/实际、证据位置、影响等级、是否可复现、推测根因、关联问题和建议处置。执行期间的“推测根因”不得当作结论；统一复盘后才建立修复任务。

## 8. 通过标准和交付物

### 批次有效

- M01—M06 均已执行，或未执行项只由第 6 节定义的全局异常阻断。
- 每个已执行场景都有浏览器、会话、Provider 调用和数据归属的可核查记录。
- 问题在批次结束后统一分类，未通过“中途修复 + 局部重跑”掩盖失败。
- `external_inconclusive` 有对应的外部失败证据，同时产品侧 deadline、恢复、账本和终态均有通过证据；否则批次按产品失败或未完成处理。

### P08 通过

- 没有 P0/P1 未解决问题。
- M01—M06 的核心断言均通过；P2 问题有明确记录与处置，不得冒充不存在。
- Provider 调用与预算闭合，且无来源、会话或数据归属不明。
- 最终报告明确证据等级仅到“真实浏览器 + 真实 Provider”，不推导为部署或生产通过。

### 交付物

1. 批次冻结记录：当前提交、输入、模型、端点、预算、矩阵版本和授权文本。
2. 全矩阵结果表：M01—M06 的状态、核心断言和证据链接。
3. 问题台账：按 P0/P1/P2 聚类，含影响和建议修复顺序。
4. 修复计划：只在批次完成后形成，并说明下一次完整矩阵的进入条件。
5. 最终验证报告：通过状态、未解决问题、Provider 消耗和证据边界。
