## 1. 核心判断：骨架不动，器官移植

**V1 的架构骨架保留**：LLM 分析师 + 工具循环 + 分层意图（9 类/4 级人设/3 级熟练度）+ 完整产品面（web/会话/项目/任务/知识/图表/导出）。
**V2/7 月线的资产作为"器官"注入**：确定性统计引擎、编译校验合同、数值自愈、非破坏性原则、版本化数据底座。

依据（全部为实测，非推断）：
- v1 骨架的广度/深度/无死路在 6 场景中全面验证（S1 超锚点、S2 超 7/11、S3/S4 为 v2 不可能任务、S6 主动澄清、S7 意图即战力）
- v1 的三个真实弱点恰好有三件现成资产可补（见 §3）
- v2 证明"窄目录+确定性"换来严谨但必然死路——其正确资产是引擎与合同，不是架构

## 2. 分层架构

```
L0 意图层（v1 原有，保留+微调）
   9 类两层意图分类、4 级人设、3 级熟练度语言分级
   ├─ 保留：闲聊/知识问答/咨询/追问/协商的分流（实测即战力）
   └─ 微调：结果追问携带上轮分析摘要（来自 7/11 会话第 3 轮的优秀模式）

L1 分析师循环（v1 原有骨架，三处强化）——产品的价值核心，S3/S6 证明不可替换
   ① 统计引擎工具化【核心移植】：v2 的 9 个确定性引擎包装为注册工具
      paired_comparison / curve_fitting / group_ranking / factor_ols /
      hac_trend / forecast_baseline / bivariate_fallback …
      - 工具描述带能力元数据（问题类型/适用条件/输出契约）
      - 系统提示+意图层引导：统计问题优先调引擎工具，run_python 退居探索
      - 效果：统计正确性由引擎保证（v2 严谨），编排自由度由 LLM 保留（v1 广度）
   ② 数值自愈：v2 planner 的列角色探测（≥95% 可转换→数值候选+披露）移植进 load_data/quick_profile
   ③ 版本化数据底座【7 月线 P1/P2】：raw 快照+分析副本+血缘（非破坏操作的物理前提）

L2 合成层（v1 原有，加装校验器）——修复"口径纪律缺失"（S4 实证）
   compile-verifier（v2 compile_answer 的标注式改造）：
   - 答案中的数值与工具/引擎输出一致性抽查（不一致→标注，不删除——7 月教训）
   - estimand/口径披露检查（总额 vs 日均 vs 窗口——S4 类分歧必须显式声明）
   - 结论分级标注（描述/关联/推断/预测/因果——超出数据范围的必须降级标注）
   - 输出：答案后附"校验摘要"（通过项/标注项），非阻断

L3 确认与门控（M1 原则原地修）——修复"确认门过度触发"（S5 实证）
   - 非破坏性操作（类型转换/派生版本/清洗副本/分析计算）自动放行+血缘记录
   - 仅真正不可逆/跨会话边界操作（删除数据集/覆盖外部文件/导出）确认
   - 高风险"方法"不再是确认理由（计算不是破坏——M2-D 已锁定的标准）

L4 完成度与状态（借 v2 思想做轻量版）——修复"断言式完成"（S2 实证：9 次调图 3 张落盘）
   - 分析计划（v1 已有 record_analysis_plan）× 真实工具执行的对账
   - 计划声明"生成图表"但 create_chart 无成功落盘 → 答案前强制补跑或如实声明缺图
   - 轻量实现：不建全量事实日志，回合内对账即可

L5 产品层（v1 原有，按审计清单增量）
   结论先行工作台（7 月线 P8-⑤ 已有实现可借鉴）、图表邻接呈现、
   多文件（v1 原生支持）、知识/记忆系统（v1 原生，继续用）

测量层（贯穿，来自两线基建）
   - golden 重放：S1-S7 + 两锚点提示词固化为常驻测试（对比行为演进，不校验内容为真值）
   - 人工评审 10+2 维（信息量/可操作性新增）
   - 场景 oracle 数值断言（引擎层的确定性测试全保留）
```

## 5. 关键设计决策记录

1. **引擎作为工具而非内部实现**：LLM 保持编排权（S3 的三文件合并、S6 的主动寻数、S2 的恒等式分解都依赖编排自由度）；统计正确性下沉到引擎。v2 的 planner 前提检查不进主流程，改造为"方向推荐器"（对齐审计 B2.7 的 Track1）。
2. **校验是标注不是门禁**：7 月线的破坏式发布已实证瘫痪；标注式让用户看到"哪句数值与计算不符"而不吞答案。
3. **完成度对账在回合内**：不建跨回合事实投影（v2 的 store/projection 留档不移植）——轻量解决"假完成"，避免第二系统。
4. **知识/记忆系统原样保留**：v1 原生（对齐审计：v2 整层缺失），后续按使用反馈优化。
5. **provider 授权纪律采纳**：成组、精确次数、无自动重试——从 v2 移植到测试与发布流程（不影响产品内正常对话）。

## 6. 原移植依赖顺序（已废止）

原提案的 R0（底座）→ R1（数据底座 P1/P2 + 自愈）→ R2（引擎工具化）→ R3（compile-verifier）→ R4（确认门 + 完成度）→ R5（产品面）→ R6（测量）是横向分层路线，现已废止。它会让真实端到端反馈出现得过晚，也默认了尚未验证的批量移植范围。当前采用配套计划中的 Slice 0–7 纵向顺序：每个切片都完成数据→工具→证据→答案→Web→产出的闭环，并回归前序能力。

## 7. 风险与开放问题

1. **编造风险的边界**：实测中"有工具时算而不编"未复现编造；但校验器是护栏不是保证——抽检维度按人工评审反馈迭代
2. **引擎工具的选择引导**：LLM 是否会弃引擎而手写 run_python？靠工具描述+系统提示+golden 测试断言（引擎调用率纳入重放断言）
3. **S4 的 estimand 标准**：配对设计优先原则写入工具描述与系统提示（同单位跨两组→paired_comparison）
4. **7 月线 P3/P4（工具参数契约/有界沙箱）**：建议随 R2 同批移植（引擎工具需要参数校验）
