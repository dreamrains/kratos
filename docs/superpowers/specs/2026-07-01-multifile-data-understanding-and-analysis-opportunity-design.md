# 多文件数据理解与分析机会设计

## 1. 目的与范围

本设计将多文件分析从“加载多个文件后由 LLM 临场选择工具”升级为一条可审计的闭环：

```text
数据载入
→ 分层数据理解
→ 关系假设
→ 确定性关系验证
→ 分析机会生成与排序
→ LLM 制定策略
→ 生成任务图
→ 执行与产生证据
→ 充分性检查
→ 补分析、重规划或最终综合
```

本设计扩展 `2026-07-01-stage-3c0b-central-data-scope-boundary-design.md`。中央数据边界仍是运行时安全基础；本设计进一步定义数据预览、关系验证、建议分析方向、提示词分层、联合分析、派生数据、重规划与用户可见体验。若两份文档的范围描述冲突，以本设计为后续阶段的产品与分析架构依据。

## 2. 已确认的产品决策

1. 跨文件关系由 LLM 提出，确定性验证器批准后才能执行。
2. 数据预览采用双层视图：用户看到决策摘要，LLM 读取完整结构化数据理解包。
3. 高价值、高置信且低风险的分析方向自动进入计划；低置信或高风险方向请求用户确认。
4. Workbench 必须帮助用户理解数据、分析价值、风险和下一步，不展示无意义的技术状态堆积。
5. Stage 3C0B 采用清晰的新契约，不保留部分新旧逻辑双线执行。

## 3. 核心产物

### 3.1 DataUnderstandingBundle

每个数据版本生成一个规范化数据理解包，作为用户预览、LLM 规划、关系验证和分析任务的共同事实来源。

```json
{
  "id": "dub_...",
  "version": 1,
  "data_fingerprint": "...",
  "datasets": [],
  "entities": [],
  "metrics": [],
  "dimensions": [],
  "time_ranges": [],
  "grain": {},
  "quality_findings": [],
  "relationship_candidates": [],
  "supported_questions": [],
  "unsupported_questions": [],
  "analysis_constraints": []
}
```

数据理解分为五层：

1. 文件清单：用途、行列数、时间范围、更新信息和粒度。
2. 质量与可用性：缺失、重复、候选主键、异常值、字段稳定性和可分析范围。
3. 业务语义：实体、事件、指标、维度、时间字段和可能回答的问题。
4. 文件关系：候选键、关系语义、基数、覆盖率、时间匹配、口径兼容性和风险。
5. 分析能力：可直接分析、可比较、可连接、需先聚合、数据不足和需确认的方向。

### 3.2 User Data Brief

User Data Brief 从 DataUnderstandingBundle 派生，面向用户展示：

- 文件分别描述什么；
- 数据时间范围、粒度和总体可用性；
- 哪些文件可能关联以及关联可信度；
- 可以和不可以回答的问题；
- 主要质量风险；
- 推荐分析路径；
- 需要补充或确认的信息。

默认不显示原始行、内部 artifact ID、工具日志或大段字段类型。样例值涉及敏感信息时必须脱敏。

### 3.3 RelationshipCandidate 与 RelationshipValidation

RelationshipCandidate 只表示关系假设，不构成 join 授权。确定性验证至少检查：

- 业务语义与字段类型；
- 数据粒度；
- 键唯一性和缺失率；
- 一对一、一对多或多对多基数；
- join 覆盖率与未匹配分布；
- join 前后行数和实体数变化；
- 时间窗口与时区；
- 指标定义、单位和人口范围；
- 选择偏差、重复计算和 join explosion 风险。

状态为 `proposed / validating / validated / rejected / needs_confirmation`。只有 `validated` 关系可用于自动执行联合分析。

### 3.4 AnalysisOpportunity

建议分析方向使用结构化对象表示，而不是一次性自然语言推荐。

```json
{
  "id": "opp_...",
  "question": "...",
  "business_value": "...",
  "strategy": "joint",
  "datasets": [],
  "required_relationship_ids": [],
  "required_checks": [],
  "expected_evidence": [],
  "feasibility": "high",
  "confidence": "medium",
  "risks": [],
  "status": "proposed"
}
```

机会来源包括用户目标、单文件分析能力、已验证关系、现有证据缺口和替代解释。排序综合考虑：

```text
用户目标匹配度
× 决策价值
× 数据可行性
× 关系可信度
× 预期证据强度
÷ 分析成本与风险
```

默认仅向用户展示排名最高的 3 至 5 个方向。

### 3.5 StrategyRecord

Planner 为选中的 AnalysisOpportunity 生成 StrategyRecord：

- 分析目标和业务价值；
- 所需数据集与关系；
- 分析模式；
- 关联键、粒度和时间对齐方法；
- 必须完成的质量检查；
- 预期中间数据和 EvidenceRecord；
- 停止条件；
- 降级与重规划条件。

确定性验证通过后，StrategyRecord 才能投影为正式 AnalysisPlan 和 TASK DAG。

### 3.6 DerivedDataset

清洗、转换、聚合和 join 产生的中间数据必须记录：

- 来源数据集与版本；
- 转换表达式和参数；
- 当前粒度；
- 行数、实体数和字段变化；
- join 覆盖率与基数；
- 所属计划和任务；
- 可见范围和生命周期。

DerivedDataset 自动继承所有合法源数据集的任务作用域。它是后续计算输入，不自动成为证据。

### 3.7 EvidenceRecord

EvidenceRecord 记录：

- 支持的问题与 claim；
- 指标值、定义、单位和统计口径；
- 样本量、时间范围和人口范围；
- 原始与派生数据来源；
- 计算方法和方法细节；
- 置信度、限制与替代解释；
- 可支持的结论强度。

只有规范化且通过验证的 EvidenceRecord 能进入综合阶段。

## 4. 分析模式与任务图

AnalysisPlan 支持四种分析模式：

- `independent`：一个原始数据集的独立分析；
- `joint`：两个或更多已验证关系的数据集进行行级联合分析；
- `aggregate_then_join`：先统一粒度和口径，再执行关联；
- `synthesis`：只读取当前计划的证据、合同、策略和验证报告，不读取原始数据。

计划投影为有依赖关系的 TASK DAG，而非仅靠顺序文本执行。关系验证任务必须先于依赖该关系的联合分析任务；EvidenceRecord 依赖对应分析或质量检查；综合任务依赖必要证据。

每轮最多自动选择 3 至 5 个高价值方向。达到问题覆盖与证据充分条件后停止扩展，低价值探索保留在“可继续分析”中。

## 5. 自动进入计划与确认规则

AnalysisOpportunity 只有同时满足以下条件才自动进入计划：

- 与用户目标直接相关；
- 数据与必要关系已存在；
- 关系通过确定性验证；
- 没有严重质量阻断；
- 方法不是需要确认的高风险方法；
- 预计能够产生明确 EvidenceRecord；
- 成本和步骤数在当前执行预算内。

低置信关系、因果/预测等高风险方法、业务口径冲突、关键键不明确或需要扩大用户问题范围时，必须请求确认。

## 6. 提示词与控制权

### 6.1 Data Interpreter Prompt

输入确定性统计、样例摘要、粒度、时间范围、质量结果和用户背景；输出实体、事件、指标、维度、字段角色、可回答问题和关系假设。它不能批准 join 或直接形成业务结论。

### 6.2 Planner Prompt

输入用户问题、DataUnderstandingBundle、已验证关系、AnalysisOpportunities、已有证据、未覆盖问题和执行预算；输出 StrategyRecords、AnalysisPlan、预期证据、停止条件和重规划条件。

### 6.3 Executor Prompt

只接收当前 TASK、允许数据、已批准策略、方法目标、证据要求、质量风险和停止条件。在当前范围内，Executor 可以选择具体统计方法、编写 Python、创建派生字段、调整聚合方法并探索异常或替代解释。需要新数据或改变核心策略时必须重规划。

### 6.4 Synthesizer Prompt

只接收用户问题、当前计划 EvidenceRecords、Measurement 定义、数据合同、限制、未覆盖问题和验证报告。核心结论必须引用 evidence ID，并区分事实、解释、未验证假设、建议、限制和下一步。

### 6.5 Context Builder

不同角色只获取必要上下文：

```text
Interpreter → 数据摘要与样例
Planner     → 数据理解、关系、机会和用户目标
Executor    → 当前任务、策略和允许数据
Synthesizer → 当前计划的证据、合同和限制
```

上下文通过 artifact ID 和紧凑摘要引用持久化产物，避免重复塞入完整预览、历史日志或无关数据。

## 7. 中央数据边界与阶段可见性

运行时使用三种数据可见性：

1. 规划阶段：可读取全部上传数据的合同、Schema、质量摘要和受限样例，用于建立 DataUnderstandingBundle；不得在计划外完成正式分析结论。
2. 执行阶段：只读取当前 TASK 绑定的原始数据和合法派生数据。
3. 综合阶段：只读取当前计划的证据、合同、策略和验证报告。

ContextAwareWorkspace 是权威数据边界。工具入口 guard 只负责提前提供可读错误，不能作为唯一权限控制。Prompt 缓存键必须包含 plan ID、task ID、scope fingerprint 和 DataUnderstandingBundle 版本。

若存在活动 Stage 3C0B 计划但没有唯一 `in_progress` TASK，执行阶段必须失败关闭，不能退回无范围限制的旧行为。

## 8. 重规划与失败处理

以下情况触发新 Plan 版本：

- join 覆盖率或基数不符合预期；
- 多对多关联造成行数膨胀；
- 时间范围、单位、指标定义或人口范围不兼容；
- 原计划遗漏必要数据；
- 中间结果推翻原假设；
- 用户问题仍未被证据覆盖；
- 当前策略无法产生所需证据。

新计划激活后，旧计划未完成 TASK 被 supersede，不允许新旧计划同时执行。失败不得通过模糊字段匹配、自动扩大权限或静默换口径绕过。

用户可见错误必须说明：发生了什么、为什么影响分析、系统将如何降级或补救，以及是否需要用户输入。

## 9. Workbench 用户体验

Workbench 围绕四类用户问题组织：

1. 我理解的数据：业务对象、时间、粒度、指标、维度、质量和可回答问题。
2. 文件关系：关系依据、字段、基数、覆盖率、验证状态、价值和风险。
3. 建议分析方向：价值、数据、策略、预期证据、置信度、风险和是否已进入计划。
4. 当前结论覆盖：已回答、分析中、数据不足、存在限制和下一步补充分析。

Workbench 不以内部 TASK 状态、工具调用日志或 artifact 数量作为主要内容。技术细节可下钻，但默认视图必须帮助用户理解和决定下一步。

## 10. 版本、一致性与失效

DataUnderstandingBundle、关系验证、AnalysisOpportunity、StrategyRecord、DerivedDataset、EvidenceRecord 和 AnalysisPlan 均记录数据指纹与版本。

文件变化、重新清洗、派生数据更新或关系验证规则变化时：

- 旧关系和机会失效；
- Prompt 缓存失效；
- 受影响策略重新验证；
- EvidenceRecord 保留来源版本，不与新版本数据混用；
- 必要时创建新计划版本。

## 11. 验收与真实数据验证

最终验证必须使用 `reference/test_doc` 中的真实文件，并覆盖：

1. Banner、内购、激励视频：独立分析、指标兼容与证据综合。
2. 省钱卡用户流水与订单：候选键、基数、覆盖率、聚合后连接和联合分析。
3. 无可靠关系的文件组合：避免因同名字段或偶然重叠错误 join。
4. 质量故障注入：重复键、缺失键、时间错位和多对多膨胀触发降级或重规划。
5. 单文件质量回归：指标数量、洞察深度和专业性不得低于现有流程。
6. 结果质量：用户问题覆盖率、证据引用率、指标口径完整性、不支持结论数量、关系验证正确性、可行动性和 Workbench 决策价值。

除单元与集成测试外，应保存一组可重复的真实数据分析基准，比较变更前后的分析问题覆盖、证据完整度、洞察深度和失败处理。

## 12. 非目标

- 不自动连接所有存在共享字段的数据集。
- 不让 LLM 绕过确定性关系验证。
- 不把 DerivedDataset 自动视为 EvidenceRecord。
- 不在一个 Prompt 中同时完成数据理解、计划、执行和综合。
- 不为旧 Stage 3C0B 部分执行路径保留兼容双轨。
- 不要求用户确认每一个低风险、高置信的分析步骤。
