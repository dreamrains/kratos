## 3. 我审计的盲区（认）

我把图表问题框定为**"agent 不调用 create_chart"**（执行侧）。Codex 框定为**"没生成的图被当完成、叙述被当答案发布"**（发布侧+状态侧）。后者才是用户看到的灾难。**我原 batch A（修图表执行）即使成功，也不阻止 false-publish——只要某次 create_chart 因任何原因没跑成，系统照样绿灯发布叙述。** 这是严重度判断失误。

## 4. 重新定位的根因（更低复杂度修法）

Codex 的 false-publish（A）+ false-complete（C）+ 审计 F3 是**同一缺口**：

> 完成度是"断言"（短语表 / 任意成功），不是"计算"（计划证据状态）。

**故障链**：
```
任意工具成功 → chart 步骤被推进(C)
+ chart 需求="limitations" 已被他步满足(F3) → 评估器判计划完成
+ 短语表抓不到"最后生成两张图表"(A) → 叙述被发布
= 绿灯任务列表 + 发布叙述 + 空图
```

**最低复杂度修法 = 修"完成评估"一个层，三 P0 同闭**：
1. 推进步骤要求"执行工具的能力 ∈ 该步骤所需能力"（比"任意成功"紧、比"binder 全通过"松，不重新耦合到坏掉的 binder）；
2. chart 步骤给**真实需求类别**（F3），其满足依赖真实的 `visual.chart` 计算 ref；
3. **发布前置 = 计划真正完成**（证据状态驱动），而非文本短语匹配。

**关键排序耦合**：单修完成评估（发布变严）而不同时修 F1（chart 真能跑），会**重新卡死**——严格的完成门等一个预算饿死的图。故这三项必须**同一批次**。

## 5. 对 Codex 处方的取舍（反驳点）

1. **"回退 M2-C、图表改条件策略"** — ⚠️ **不回退 M2-C**。M2-C 加 chart 步骤是因为没有它 agent 根本不画图（记忆验证：plan 无 chart cap → createChartMentions=0）。回退=回到"从不画图"。正解是**让 chart 步骤真能执行（F1/F2）+ 按数据形态条件纳入**，不是删步骤。Codex 在此把"执行失败"误诊为"步骤多余"。
2. **"运行中输入改发送/引导+停止两动作"** — ❌ **本期不做**。运行中引导分析（注入 guidance、排队语义）是新功能，对一个"复杂度增长快于验证"的项目是错误的第一步。先止血，引导能力入 backlog。
3. **"删 strict/tiered publication 分支"** — ⚠️ 是清理非修复。审计已确认这些分支 dormant（live loop 恒 transparent）。删它不修任何 P0，排后。
4. **统计口径** — "225 文件 / 7.2 万行"是**全仓库**（含 tests/sessions/生成物）。**src/ 实际 69 文件 / +24,790 行**（`git diff --stat -- src/` 实测）。loop.py 33 次、answer_quality.py 22 次提交属实。
