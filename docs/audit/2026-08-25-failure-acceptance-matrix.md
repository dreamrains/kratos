## 1. 验收原则

1. **先证明会失败，再修复。** 每个历史事故先形成 provider-neutral RED 测试或可复算 oracle；不能只靠 prompt 或文档约束。
2. **修共享契约，不修单份答案。** 同一根因影响多个场景时，只在数据身份、工具结果、任务状态、发布或 Web 事件等公共边界修复。
3. **分开四类证据。** 单元/契约测试、离线 Agent 回放、本地真实 Web 进程浏览器、真实 Provider 是四种不同证据，不能互相冒充。
4. **证据绑定当前源码。** 收据至少记录 source digest、数据内容指纹、场景 ID、模型、prompt、调用次数、浏览器构建和时间。
5. **真实 Provider 严格授权。** 只有用户明确批准某个冻结批次和精确调用次数后才执行；失败即停止，不自动重试、修复后补调或换模型续跑。
6. **质量不是“能输出”。** 正确性、范围完整、方法合适、证据绑定、业务解释、建议安全、图表真实性和交互完成都要验收。

## 6. 分析质量评分门禁

每个真实 Provider 场景由独立评分表按 0–4 分评估，必须同时满足：

- 所有 F01–F33 适用的零容忍项通过；
- 下列核心维度必须为 4：数据范围与绑定、数值/事实正确、方法适配、完成/发布真实性；
- 其余适用维度均不低于 3；
- 不使用平均分掩盖单项失败。

评分维度：

1. 问题理解与目标覆盖；
2. 数据范围、版本、粒度和口径；
3. 方法选择与假设；
4. 数值、统计和证据严谨性；
5. 不确定性与结论校准；
6. 竞争解释和敏感性；
7. 多步骤/多文件综合；
8. 金字塔表达与业务翻译；
9. 图表必要性、真实性和可读性；
10. 建议的证据、优先级、适用范围和可执行性；
11. 信息量与简洁度的平衡；
12. 交互、进度、停止、恢复和产出可靠性。

禁止把现有会话当质量标杆。对比会话只用于发现能力差异、事实错误、信息损失和表达差异；所有数值必须由当前数据重算或由固定 oracle 验证。

| 层级 | 内容 | 通过含义 | 不能声称 |
