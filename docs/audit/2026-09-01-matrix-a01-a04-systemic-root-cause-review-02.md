## 为什么多轮修复后仍反复失败

问题不在单个函数，而在同一分析事实穿过多个彼此独立的契约：工具结果、收据详情、证据字段、图表数组、工作台状态、公开回复和导出文件分别判断。前一层算对，不保证后一层能读取、验证或安全发布。

早期离线用例覆盖了理想脚本形状，没有重放真实模型产生的组合：嵌套统计字段、`analyze_time_series` 结果、numpy 风格沙箱文本、同秒多证据、长详情读取、工具能力与参数不匹配、多段回复及错误后的手工图表。每次真实批次因此都在上一轮未覆盖的下一层暴露缺口。

系统还混用了七种“完成”：请求终态、分析轮完成、任务计数、证据完整、允许发布、导出身份、进程退出。A01、A02、A03 分别证明这些状态不能互相代替。A04 又证明“检测到语义违规并失败”仍不够，因为被拒文本已经进入了 UI 与导出投影。

最后，A04 M04 的停止不是产品分析失败，而是操作入口重复要求手工填写已经被批次摘要承诺的派生摘要；遗漏 `sha256:` 前缀便触发冻结不符。这个入口增加了人为失败面，没有增加安全性。

## 本次系统性修复

1. **证据投影**：支持 `analyze_time_series` 的真实字段；缺失观察窗口时，只能从当前收据绑定且身份已验证的数据集推导；补充性非类型化沙箱结果不再抹掉充分的原生统计证据；模型自填的 `time_scope_source` 会被移除并重新计算。
2. **发布隔离**：第一次不合格 final 只保留在内部历史并标记 `publication_rejected`，不进入 UI 或导出；系统只允许一次基于现有证据、禁止再调用工具的改写；第二次仍失败则关闭发布。内部标记在 Provider 形状历史中被剥离。
3. **冻结入口**：外部只需要授权批次摘要；程序从候选文件重算源码、启动器、监督器、数据、提示词、oracle 和 case 摘要，并把已经核验的源码与启动器身份传给下一层单场景守卫。旧调用若继续提供派生摘要，任一不符仍 fail closed；等价的裸 64 位摘要也可规范化接受。
4. **真实形状回归**：新增 A04 实际结果形状、证据重投影、补充沙箱与原生证据组合、公开投影隔离、一次改写和单摘要授权测试。

没有增加 Provider 额度，没有 fallback、重试或并行 V2，也没有放松收据、数据归属和进程退出边界。
