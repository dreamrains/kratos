## 2. 为什么会反复修补

以下将事实与判断分开；代码体积只说明维护范围扩大，不能单凭行数判定质量。

| 已核实事实 | 对进度的影响 | 重建措施 |
| --- | --- | --- |
| 当前 `AgentLoop` 的 `typed_trial` 默认关闭，候选注入依赖该开关；大量生产者以 offline/opt-in 存在 | 普通全矩阵、离线投影和自然 typed 试验不是同一个验收对象，无法累积成一条退出证据 | R2 先接同一正常 app/AgentLoop 路径，固定候选配置；R5/R6 对该配置验收 |
| `publication_synthesis.py` 从 2136 行扩到 4856 行，旧正文校验与新 binding、preview、trace、partition 同时存在 | 新增机制没有对应删除旧决策路径，正确结果可能仍受旧门影响；问题可能来自另一条路径 | 按职责迁移，每一旧门列替代物、保留正例和禁止误放反例，R5 必须完成实际退役审查 |
| 多轮离线工作最终仍是 `answer_coverage=unassessed`、`publication_effect=none`；自然完整批次仍有 0 typed 的情况 | 协议字段存在、回放成功不能证明自然生产与用户需求闭环；大量测试覆盖的是辅助函数 | R2/R3 的完成条件必须包含 app 路径生成的最终答案、回执、持久状态；不以新增 helper 或测试数量交付 |
| 历史综合/聚合回执、最终 packet、当前 audit input 的事实范围不同 | 宿主已知道的数据未必能在发布或审核处使用；追加审核字段不能解决上游选取与生产缺口 | 先解决同 packet 的已执行结果身份与选择，再建设解释审核；不另建事实权威源 |
| 最新自然 Shadow JSON 有效，但固定关键风险仅命中 1/4，两个宿主引用均误报 | “接口可调”没有成为“可安全自动修订”；继续把 Shadow 作为必过总门会拖住全局 | Shadow 保持诊断；R4 对语义能力做一次完整设计与有界校准，失败必须裁决能力范围，不能继续逐句调提示词 |
| 总计划、stage-status、handoff 同时承载当前状态与长历史；早期和后期结论并存 | 每次续接容易把准备项当完成项，或把历史授权/入口重新解释一遍 | 只保留总计划一个当前看板；历史文档保持证据身份，不继续复制当前状态 |

核心判断：阻塞来自**验收对象不统一、生产链未先闭合、机制与产品完成混淆、开放语义目标缺少有界决策**。换目录不会自动解决这些问题；必须同时改变任务组织与验收方法。
