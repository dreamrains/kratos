## 4. 已核根因与仍需验证的部分

1. **辅助分类与需求入口不一致。** 完整请求响应中，53次 JSON 辅助调用包括27次65536-token正常完成、26次300-token `finish_reason=length`；26次小预算均不完整。M01第4/5调用两个截断分类，随后咨询暂停。`_prepare_analysis_turn` 使用一个分类/需求输入，`_build_system_prompt` 又通过 `_classify_task` 建立另一分类与提示层级，真实路径存在重复且失败语义不一致；不能仅将上限从300增大便宣称修复。
2. **不合法 selector 删除了原需求。** M03第21调用与M04第31调用的完整 JSON 已识别结果/竞争假设原文，却给出缺少 tool 的 selector。`llm_intent.py` 对 selector 校验失败执行 continue，整个输出项被移除；state只保留 presentation。M02则保留结果文本但没有 selector，`bind_requirements` 不接纳模型终局 claim refs为绑定，因此正确事实兜底与覆盖/开放解释相互脱离。问题在原需求保全和语义目标绑定，不在散文词汇。
3. **咨询豁免不能靠分类标签独立授权。** M03续问 `ans_e1e02d799d864c45de524dc1ef8835adfad0ab4eeb2c2f1578590a696bda526b` 的真实冻结快照为 consultation/claims0/uses_result_context=false，实际模型却接触了既有分析。含来源金额的续问仍作为 knowledge 文本接受，跨来源总量违反原 oracle。修复须根据宿主真实上下文与原答案身份决定数据路径；纯知识咨询能力必须保留。
4. **需求生命周期与版本/范围没有贯通。** M05旧风格未完成需求持续进入新回合，plain段被旧analyst需求拒绝；`snapshot_for_turn` 给旧无 source_answer_id 的摘要套用当前追问缺口。M04自动上传别名、计划/任务scope及终局快照变化不同步；M06自动上传别名没有执行用户精确名称要求，typed confirmation正确绑定实际别名，driver正确拒绝了不相等冻结身份。需要保留数据版本/任务隔离的限制并补齐实际入口，不能放松scope或把近似标签当授权。
5. **验收的端到端缺口。** P4的固定分类/selector/审核候选验证了合同，但没有证明上述自然输出能穿过默认入口。多数本地结构保护仍有效；真实请求—分类—需求—工具—确认—快照—可见正文关系不足。需要用本次已捕获原材料形成离线自然反例，避免扩大同型测试数量后再次付费试错。

已进一步用原自然响应通过现有 `classify_intent_llm` 做零网络解析复现：M03的4项提议只保留2项、M04的3项只保留1项，丢失的正是主要结果需求；M02四项仍保留但没有selector。机器材料为 `natural-parser-replay.json`，实际Provider调用0。这只验证原解析器入口的反例，不冒充完整AgentLoop离线重放或修复后的通过。

第1/2/3项有完整自然输入及源码对应；其相互因果程度、路由合并和语义绑定的最终接口仍需离线回放决定。第4项具体失败已有证据，但不将“所有版本实现都错误”当结论：P4同别名正负例仍保留。
