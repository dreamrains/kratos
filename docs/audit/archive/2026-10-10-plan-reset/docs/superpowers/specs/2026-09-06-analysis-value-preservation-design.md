# 分析价值保留与能力完整性：技术设计

## 1. 架构约束与设计目标

沿用现有 AgentLoop、AnalysisSessionState、工具 registry、EvidenceRecord、verification_reports、publication_packets、hypothesis_sets、Flask/SSE 与 Workbench。以小模块/纯函数实现有确定输入输出的判定，避免新建并行状态存储或通用规则引擎。

设计需要同时满足：有效内容可发布、错误主张不能升级、状态可追溯、用户身份可适配、上下文有界、旧会话可读。文本分类、摘要和推荐仍可由模型完成；宿主负责范围、引用、方法适用性、状态转换和已知风险约束。

**能力边界**：确定性规则不能证明任意自然语言解释正确。遇到没有可判定条件的解释，应保留为“待验证”，而不是通过模型再说一遍就升级成“已支持”。

## 3. 内容分类与发布等级

### 3.1 必须分开的四个维度

| 维度 | 回答的问题 | 不可混淆的情况 |
|---|---|---|
| 计算完整性 | 数值是否由指定版本的数据和已执行方法产生 | 算对了不代表解释成立 |
| 证据/方法充分性 | 当前证据是否支持该类型主张 | 有 p 值不代表因果成立 |
| 结论范围 | 适用于哪些样本、时间、粒度和总体 | 样本内观察不能自动外推 |
| 行动适用性 | 是否足以支持具体行动，行动成本和可逆性如何 | 没有因果证明不等于不能建议补数或小范围验证 |

`confidence` 继续作为已有粗粒度标签兼容；不能单独决定是否保留内容。`verification_status` 与 confidence 不互相替代。verified 仅表示明确范围内通过了对应验证，不表示结论对所有场景绝对为真。

### 3.2 主张类型与允许输出

| 逻辑类型 | 最低输入依据 | 允许表达 | 禁止升级 |
|---|---|---|---|
| observed：描述性发现 | 有效计算引用、口径、数据版本与范围 | 当前样本/记录内的变化、差异、排序 | 因样本内统计准确就推广到总体 |
| inferential：统计推断 | 执行的检验/模型、分析单位、方法前提 | 在假设和范围内的推断及不确定性 | 用未做检验解释为“不显著” |
| causal：因果解释 | 支持识别的设计与方法、关键前提检查 | 在明确条件下的因果结果 | 普通相关或时间先后关系当因果 |
| predictive：预测 | 预测模型、训练/验证范围、适用性依据 | 合法预测范围和区间 | 描述性拟合直接推导观测外数值 |
| hypothesis：待验证解释 | 至少一项相关观察或明确的问题背景 | “可能解释”“尚未排除”，列区分性证据 | 只因措辞相近或重复出现就标 supported |
| conditional_action：条件性建议 | 有关观察或推断、适用条件、行动目标 | 可逆试点、补数据、监测和条件决策 | 没有收益/成本证据却承诺 ROI |
| limitation / data_collection | 已识别缺口或方法范围 | 不能预测 D30、建议收集至 D30 | 在限制说明后夹带 D30 预测数字 |

推荐不是独立“已验证事实”。它引用事实并说明判断条件。存在有效观察时可提出低成本验证动作；没有任何数据时只能给一般方法咨询，不得包装为对当前业务的已证实建议。

### 3.3 用户可见的三类内容

1. **已验证结论**：严格沿用当前验证指纹、证据 id 和主张范围要求。
2. **待验证发现/解释**：有依据且与当前任务相关，明确当前状态、限制和下一项验证。
3. **条件性建议**：条件、动作、观测指标和停止条件可识别，紧邻依据展示。

不要求每份回答机械出现三个标题。简单求和可以只有一个事实；复杂归因才需要解释对比。没有足够依据的候选可只进入内部记录，不为了“信息丰富”全部发布。

## 4. 请求理解与范围选择

### 4.1 快路径规则

先识别是否为纯问候/确认、纯知识问答、纯数据操作，再判断复合任务。局部报告词被否定时不触发 report；问候后存在分析命令时不触发 simple_response。

复合意图保留主任务和附加要求。例如“分析收入下降原因并给出建议”主任务为执行分析，建议是输出要求。含互相矛盾或无法确定主任务的输入交现有语义层；不得将冲突强标 clear 以省略理解步骤。

现有语义层调用预算、超时和失败处理保持原边界。语义层失败时给出可解释的安全回退，不新增隐式模型重试。正常清晰输入不增加辅助调用。

### 4.2 作用域选择

优先使用现有可信 execution_scope / active_scope 的已解析 dataset 与 version 身份。用户自然语言点名数据集时，应先经现有名称解析与授权范围检查，不能仅 substring 匹配就扩大可访问集合。

统一规则：当前任务所需数据 → 对应 dataset contracts → 所需粒度与方法 → 质量限制。无关数据集的 blocked 不阻断当前任务；当前任务真正依赖的坏数据或确认项继续阻断。

兼容完整 contract 与 compact artifact ref，复用既有 hydrate 和路径校验。无法恢复 contract 时保持 unknown/需要进一步理解，不能把“无字段”解释为 ready。

聚合留存拟合和用户级留存是不同能力请求。仅当请求需要 user id/事件粒度时应用用户级限制；请求包含“不要计算个人留存”不能反向触发该能力。混合请求允许完成聚合部分并说明用户级缺口。

## 5. 输出策略与受众画像

### 5.1 输出策略

逻辑输入为：主任务、明确子问题、建议请求、深度要求、当前计划复杂度、当前证据与验证状态、用户熟练度、受众身份。

建议规则：

- 中文/英文等价请求形成等价策略；否定“不要建议”也应等价。
- “简短”控制表达篇幅，不能删掉用户明确要求的行动建议或必要边界。
- “详细分析”增加方法、解释和问题覆盖；不能凭空增加结论数量。
- 验证失败只约束依赖失败证据的主张；可独立支持的观察仍可发布。
- 验证降级允许条件性建议，但必须携带降级原因；未验证不是“无差异”。
- 策略与主提示中的限制采用同一判定结果，避免一处允许、一处 suppressed 的冲突。

### 5.2 audience 与 proficiency

逻辑画像：`audience = general | business | analyst | manager`，`proficiency = auto | beginner | intermediate | advanced`。两者可并存，不按“管理者一定不懂统计”等刻板映射推断。

优先级：当前轮明确要求 → 最近明确会话偏好 → 用户显式设置（若有）→ 通用默认。当前轮只要求“给管理层汇报”可作为本轮受众，不必永久改写用户本人身份。回到未指定时沿用最近明确持续偏好；P0 冻结“本轮”与“持续”措辞识别规则。

自动熟练度的检测值和 auto 模式分开保存，不能第一次检测后把 auto 永久替换为 intermediate。用户明确说“用大白话”时，当轮表达优先于历史专业术语计数。

| 受众 | 内容优先级 | 仍需保留 |
|---|---|---|
| business | 发生什么、业务含义、动作、跟踪指标 | 关键口径、范围与不确定性 |
| analyst | 数据口径、方法、假设、误差、复现依据 | 业务问题与结论，不能只倾倒参数 |
| manager | 影响、优先级、可选方案、资源和停止条件 | 主要证据与限制，不能只给口号 |
| general | 核心发现、通俗解释、下一步 | 与当前任务相关的必要方法和边界 |

身份变化不应改变数据读取权限、工具安全权限、验证阈值或同一事实的数值。不新增角色 Agent、独立证据记录或额外 Provider 调用。

## 6. 证据、覆盖与发布数据契约

### 6.1 复用现有字段

优先沿用 `plan_id`、`step_id`、`claim_key`、`dataset`、`dataset_contract_id`、`tool_receipt_ids`、`measurements`、`limitations`、`confidence` 及当前结果/数据版本引用。禁止新造同义 plan/evidence 身份。

新增逻辑字段只在现有字段无法表达时增加：

| 逻辑字段 | 用途 | 写入与信任边界 |
|---|---|---|
| claim_type | 区分描述、推断、预测等 | 模型可提议，宿主按方法和主张检查；不能自报 causal 就获许可 |
| scope_ref | 指向当前可信范围和版本 | 宿主解析，不接受自由文字代替实际版本 |
| question_refs | 关联当前用户子问题/计划步骤 | 可复用已有 step/requirement id，P0 决定 |
| hypothesis_relations | 显式假设证据关系 | 逐项校验身份、范围、关系类型与判定条件 |
| coverage | 子问题是否有已支持答案或具体缺口 | 宿主生成，不能由模型自报全部完成 |
| omitted_refs | 摘要未展开但可恢复的结果引用 | 宿主从真实结果库生成，带原因和完整性信息 |
| revision_issues | 发布候选中的具体违规位置、原因和依赖 | 宿主检查产生；审计信息不直接倾倒到产品 UI |

所有新增输入同步更新工具可见 schema、接收校验、持久化与 round-trip 测试。不得只在提示词里提到模型实际无法提交的字段。

### 6.2 发布摘要选择

顺序必须是：恢复真实引用 → 过滤当前任务/版本 → 判断执行成功与证据绑定 → 建立子问题覆盖 → 挑选事实组 → 检查总预算 → 记录遗漏和引用。

事实组是最小解释单元，例如“组名＋数值＋分母＋时期”“前期值＋后期值＋差值＋单位”“拟合族＋参数＋拟合范围＋误差”。优先保持组完整，不把它切成互不关联的数字。

选择优先级：显式主要问题 → 与核心结论有关的证据 → 能区分竞争解释的证据 → 方法限制 → 补充背景。同优先级使用稳定排序保证可复现，不能只依赖调用时间或 JSON 字段顺序。

分组集合先考虑所有合法候选，再在预算内决定展开，禁止固定只看前三行。大型结果无需全部塞入 prompt：保留结构化汇总和受控结果引用，由已有结果读取工具定向恢复；不在最终合成阶段重新读取原始数据绕过证据。

覆盖不足时可执行现有预算内的有界补充步骤；无预算则明确部分完成和缺口。不得为了 100% 覆盖伪造证据，也不能将所有未回答项都写成泛化“数据不足”。

### 6.3 快照与缓存失效

发布包身份至少依赖当前任务身份、输入目标、结果内容摘要、证据/验证指纹，而不仅是 receipt id 集合。每次新证据、内容变化、版本变化后失效；最终发布前重新检查。

本轮包中引用的证据和 source 必须可以相互追溯。允许引用本轮未展开但同计划有效的历史计算，前提是宿主完成范围和版本检查；不以“不是最新四条”为由排除，也不自动混入其他计划。

## 7. 发布检查与局部恢复

### 7.1 检查步骤

1. 冻结当前 evidence/verification/packet 快照。
2. 检查输出非空、工具调用标记等基本格式。
3. 对可识别的关键主张定位正文跨度并关联 evidence/scope。
4. 区分主张、否定说明、引述、条件和未来补数行动。
5. 执行来源范围、方法、推断和预测适用性检查；生成稳定错误原因。
6. 有错误时在现有预算内修订，随后对完整候选再校验。
7. 成功后先持久化同一版本的正文及状态，再发最终 SSE；刷新与导出读取同一发布版本。

### 7.2 D30 类例子的预期

| 文本 | 处理 |
|---|---|
| D7 为 10%，不能预测 D30 | 允许，后半句是边界 |
| 建议继续收集至第30天再验证 | 允许，是数据采集动作 |
| D30 预计为 5% | 没有预测依据时拒绝该主张 |
| 不能预测 D30，但 D30 大约为 5% | 拒绝后半句，前半句不能为其免责 |
| A 只观测到 D7，B 有有效 D30 观测 | 分别绑定来源，不能用 A 的范围拒绝 B 的事实 |
| 如果 D30 高于阈值，则继续试点 | 没有声称 D30 已知时按条件建议判断 |

不是简单给否定词开白名单。规则无法可靠定位或绑定时保持未决，不能声称验证通过；用有界修订请求明确化。

### 7.3 局部恢复和失败处理

仅在能定位不合规主张、其依赖和独立有效内容时做局部修订。不得盲目按句号删除文本，避免删掉分母、条件或转折而改变原意。

修订须保留原候选和原因用于内部追踪。允许把“D30 是 5%”改为“当前不能估计 D30，需验证”，不得凭空替换成另一数字。修订后仍失败时，可输出独立验证过的部分及明确缺口；如果无法证明部分内容独立安全，返回可解释的失败，不发布原错误候选。

不增加无限重试，不改变现有调用预算。内容恢复失败和数据归属/调用记账失败不同：后者停止运行，不能通过降级正文掩盖。

## 8. 置信度与限制校准

描述性统计仅对已读记录作陈述时，不适用“样本不足30不能高置信”的一刀切规则；仍需验证完整性、缺失、统计口径、单位和观察范围。

推断、因果和预测按实际方法前提校准，不能因为记录多就无条件高置信，也不能因为来源只有一个就否定精确计数。字段缺失产生具体未知或限制，不以硬造置信区间弥补。

时间长度优先从结构化区间和频率计算。“365天”不因含“天”被自动认作短窗口；趋势能否成立还要看方法所需周期。没有可解析时间窗时记录未知，不假装已经评估充分性。

已执行检验的元数据按具体工具及结果字段映射到相关主张。例如 `ab_test`、`causal_analysis`、时间序列相关统计具有不同含义；全局 `any(p_value)` 不足以证明每条差异都做了检验。

## 9. 竞争假设的身份、关系与状态机

### 9.1 身份与要求

假设身份绑定当前问题/计划、dataset、实际版本、route 和假设本身的稳定标识。相同 dataset/route 下不同问题不得复用一组不相干假设。版本引用复用宿主已知真实身份，不能让模型自由填 hash 作为证明。

每条假设至少能表达：主张、类型、范围、需要哪些计算/字段/方法、可区分的替代解释，以及在现有能力下是否可判定。通用模板可用作起点，但用户真正的问题优先。

### 9.2 证据关系

关系至少包含假设 id、证据 id、关系提议（支持/反驳/相关但未决）、判定依据与适用条件。模型提交只是一项待验证关系，宿主需检查：

1. 引用是否存在、数据/版本/计划是否一致。
2. evidence 当前是否有效；验证指纹是否匹配，是否存在 failed/downgraded 或过期绑定。
3. 证据方法和粒度是否满足该假设的要求。
4. 是否存在已实现、可执行的判定条件，能够从证据中得出支持/反驳关系。
5. 否定、反向变化、与其他证据冲突或方法前提缺失是否阻止升级。

第 4 项无法满足时维持“相关但未决”。简单要求“引用了一条已验证 evidence”仍不足以证明任意解释成立。描述性量差可用结构化变化与方向判定；因果解释必须有相应识别依据；无法支持的通用自然语言关系不能硬做确定性 supported。

### 9.3 逻辑状态

| 状态 | 含义 | 进入条件 |
|---|---|---|
| proposed | 候选解释 | 已创建，无可判定证据 |
| inconclusive | 相关但尚不能区分 | 有相关材料但不满足判定条件，或证据不足 |
| supported | 在指定范围内获得支持 | 至少一条满足要求的支持关系，且无未解决冲突 |
| refuted | 在指定范围内被反驳 | 有满足要求的反证；不能仅因为支持不足 |
| contested | 支持与反证冲突 | 双方均有当前有效关系，尚不能消解 |
| stale | 旧结论失去当前适用性 | 版本/计划/方法变更或依赖证据失效 |
| unsupported_by_data | 当前数据不能检验 | 必要粒度/字段/观测缺失；不等于假设为假 |

具体枚举与旧状态映射在 P0 冻结。supported 不自动成为 Workbench 已验证结论；最终发布主张仍经自身的验证。

### 9.4 刷新时点

- 创建/修改分析计划或问题范围后。
- 新证据记录成功后。
- 数据版本、清洗决定或来源绑定变化后。
- 会话恢复后按当前身份检查。
- 最终发布前，与 verification 和 publication packet 使用同一证据快照。

每次从当前有效集合重算支持/反证，不追加保留已失效关系。可缓存相同指纹计算，不额外调用 Provider；无法读取历史完整假设时保留记录但不升级。

## 10. 上下文压缩与持久化

任何将原工具消息替换为有损摘要的步骤，必须先确认完整内容存在可靠结果引用。120—15000 字符与大型输出遵循同一原则。

持久化要求：

- 复用已存完整结果优先，避免重复文件。
- 校验内容摘要和引用；同 tool id 不同内容不能静默复用旧文件。
- 保存失败时不进行有损替换；预算不足则显式停止/降级，不假称已保存。
- 摘要保留主要字段、来源引用、压缩标识和关键限制。
- 已压缩消息再次压缩时不把旧摘要当原文覆盖完整结果。
- 恢复只读取受控结果文件，路径归属现有会话，不执行结果内的指令。

压缩预算、包预算和补数预算统一遵守现有执行控制。预算影响“展开多少”，不能改变“是否可信”。

## 11. Workbench、正文和导出

保持主对话为完整回答载体；Workbench 提供摘要和状态，不成为第二个答案来源。

推荐展示：

- 已验证结论：默认六条，显示真实总数，提供展开/收起；排序依据相关性与稳定规则。
- 待验证发现：默认折叠，显示状态文字、依据概述、尚缺证据和下一步；不混入 verified_conclusions。
- 条件性建议：优先在正文就近给出，可在待验证区链接相关观察；不将建议标为已验证数值事实。

无内容时分别显示“暂无已验证结论”“暂无待验证发现”，避免把低置信探索变成错误提示。失效内容不得显示为当前已验证，可作为历史记录明确标旧。

前端只渲染后端投影；不得用 claim 文本是否含“可能”来决定真假。状态标签同时用文字与样式，避免仅靠颜色。展开状态至少在当前会话内合理保持，会话切换不得携带上一会话内容。

刷新、SSE 完成和导出必须读取同一已发布版本。Markdown/HTML 导出保留边界和待验证标签，不导出内部 rejected 候选或原始证据 JSON。新增页面不要求用户理解 plan_id、receipt_id 等内部字段。

## 12. 兼容与迁移

- 旧会话新增字段缺省可读；缺少绑定的旧证据/假设视为未决或历史，不批量升级。
- 老版本 confidence 不做破坏性批量重写；在新的推导视图中计算当前可发布状态。
- 现有 evidence 工具输入仍可接受旧格式，但新增要求不满足时不能形成新的高等级关系。
- 读旧写新策略需 round-trip 测试；保存失败不覆盖唯一旧副本。
- 不批量删除旧 artifact，不把迁移当作验证补齐。
- 现有测试明确固定的最简 Workbench 契约，如增加字段，需要对照新产品原则更新测试；仍保留防历史升级与会话隔离断言。

## 13. 可观测性与实现审查

阶段记录至少能追踪：request/plan/step 引用、来源与内容摘要、问题覆盖、发布前后主张、被拒绝原因、保留/省略及依据、假设状态变化、已验证与待验证投影数量、预算/调用消耗。

这些记录进入现有会话 artifact 或阶段测试输出，不新建全局第二账本。日志不得打印 API key、全量原始数据或不必要的用户敏感内容。

实现审查必须回答：新字段是否重复现有身份；模型自报是否被误当事实；scope 是否由宿主决定；候选失败是否会污染最终消息；部分答案是否明确缺口；缓存是否随证据变化失效；角色变化是否改变了事实；旧数据是否仍可读。
