## 结论

当前同时存在**实现控制失衡**和**验收控制失衡**，不能继续按场景逐个加 builder 或门槛。

- 传输、账本、SSE 单终态、持久化、上传票据和部分封闭事实已经明显收敛；`71e23d0` 的 M02、M03 非视觉 oracle 通过，前批的日期、pivot、缺数据单动作和稳定确认值也没有复发。
- 仍失败的 M01、M04、M05、M06 不是四个互不相关的小缺陷。共同边界是：宿主事实块发布后，默认关闭的语义审核不能释放开放候选，正确的行动、假设审计、表达改写和状态解释被整体扣留。产品由“可信完整回答”偏成了“安全事实摘要”。
- 真实批次被用于发现本可由零调用路径审查发现的静态缺口：M04 没有可见假设审计 renderer；M05 的样式候选在当前默认配置下必然被扣留；M06 的确认后局部交付只覆盖聚合路径，真实场景走描述/Python 摘要；M01 的行动交付依赖关闭的试验审核。说明 Provider 前置门没有核对“需求—实际路径—默认配置—可见 oracle”。
- 验收身份发生混用。工作包 A 的 M05 是边界聚合，真实 P08 的 M05 是六轮表达改写；Provider 禁用联合矩阵以 `--edge` 通过，不能证明真实 M05-STYLE。M04 的“结构状态存在”也曾被写成“两轮正常执行”，但原目标要求可见、可审计的竞争假设交付。内部状态或代码入口被过早折算为用户行为通过。

因此，问题不是“真实模型每次随机挑出一个新问题”这么简单。确有自然模型波动，但当前主要风险是：实现通过累加分支吸收每批失败，验收又用不同场景、内部状态或 scripted E3 替代同一可见目标，导致下一批继续暴露另一层静态缺口。

## 目标重新对齐

原目标保持不变：

1. **VP：**当前同版本且可核的观察、方法、图表、关系与合理解释必须保留；未知、旧版、因果与未来条件不得升级。
2. **IC：**只为真实业务口径歧义暂停；确认绑定范围与版本，skip 不授权结果。
3. **CP：**每个明确子问题有答案或具体缺口；局部失败不吞独立正确值；正文、SSE、持久化、图表、导出与刷新保持同一身份。
4. **事实权威：**结构化 evidence/claim 与宿主闭合计算负责事实；模型负责开放解释；有界审核只处理开放片段，不能增加事实或覆盖确定性失败。

当前偏离发生在第 1、3、4 项之间：事实权威得到强化，但解释与需求覆盖被宿主早返回整体吞掉；为了恢复价值又不断添加场景专用逻辑，使单次终局更复杂。下一阶段必须修复**一次终局内容组合边界**，不能把 M01、M04、M05、M06 当四条独立补丁线。

## 控制重置方案

### 1. 暂停扩写和真实调用

- 在控制清单完成前不新增 claim family、builder、散文词表、审核调用或 Provider 批次。
- `71e23d0` 保持已冻结代码基线；批次收据和唯一计划可以继续更新。刚开始但未完成的 M06 计划身份放宽已撤回，产品代码当前没有未提交差异。

### 2. 统一验收身份

- 不再复用一个 M 编号表示不同任务。至少区分 `M05-STYLE` 与 `M05-AGG-EDGE`、`M06-MISSING` 与 `M06-CONFIRMED-PARTIAL`、`M04-VERSIONED-HYPOTHESIS`。
- 每项固定同一输入、默认配置、实际调用路径、可见正文 oracle、持久化/导出 oracle和负例。E2、scripted E3、自然 E4 只改变证据等级，不能更换任务含义。
- “内部状态正确”“工具执行完成”“存在宿主入口”只算前置条件；用户可见答案与独立 oracle 才能签收目标行为。

### 3. 零调用能力门

为每个真实场景先列出：入口、实际工具、packet 字段、claim/开放片段、renderer、审核开关、需求覆盖更新、可见终局。任一必需路径不存在、被默认开关关闭或只在另一场景出现，就不冻结 Provider 批次。

先用已保存的自然候选、回执、确认快照和持久会话离线重放 publication boundary。重放不能满足可见 oracle 时，真实模型再调用没有诊断价值。

### 4. 收缩核心实现

- 先为 `publication_synthesis.py`、`publication_audit.py`、`loop.py` 建调用者—行为—测试—真实收据清单，标出 live、重复、legacy fail-closed、无当前调用和仅内部审计用途；没有双向证据前不宣称死代码。
- 将终局选择、绑定、渲染、覆盖更新和开放片段审核收敛为一次顺序；`loop.py` 不再增加场景分支。保留一个 `answer_bindings.v1`、一个 render trace、一个需求覆盖权威。
- 下一产品代码工作包要求核心三文件**净行数不增加**，新增行为必须同时合并或删除旧路径。仅把代码搬到新文件不算收缩。
- 优先删除已被宿主闭合事实替代的重复散文决定权、重复 coverage 更新和不可达兼容分支；保留 schema/digest、版本、单位、算术、确认、持久化和单终态保护。

### 5. 一次系统性内容组合

在原 `answer_bindings.v1` 中区分宿主事实片段和受限开放片段：宿主始终发布闭合事实；开放片段必须绑定当前需求及允许引用的 claim，审核只决定该片段是否发布。审核关闭或不可用时，宿主事实仍交付，并把对应开放需求明确标成具体缺口，不能静默声称完成。

M04 的结构化假设状态和 M06 的 `computed / not_computed / evidence_insufficient` 属于宿主可闭合内容；M01 条件行动与 M05 表达方式属于开放片段。它们共享一次组合机制，不各自复制一套终局。

### 6. 再进入验收

顺序固定为：历史自然收据离线重放 → 定向正反测试 → 新目录 full-offline → 同一矩阵 Provider 禁用正常 app → 必要视觉路线 → 新提交精确冻结与一次自然 Provider 批次。下一真实批次前必须证明六项都存在实际可达路径，且所测默认配置与拟交付默认一致。

如果下一批仍暴露一个在零调用清单中本应发现的静态缺口，应判定控制重置失败并停止继续补丁，而不是立即准备下一批。
